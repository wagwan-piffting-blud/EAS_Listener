This is the codebase for a project called EAS_Listener. This codebase is a Rust project designed to listen for and relay Emergency Alert System (EAS) messages. The project is structured to handle incoming EAS messages, process them, and then relay the information to designated endpoints or systems using Apprise, Icecast, or MYOD (Make Your Own DASDEC; see https://github.com/wagwan-piffting-blud/MYOD/tree/cross-platform-with-audio).

When working with the codebase, it is important to understand the following major components of the project:

**Two Dockerfiles**: The project includes two Dockerfiles, one for the "full" version of the project, which includes all dependencies and features, and one for a "minimal" version, which is designed to be more lightweight. The full version is intended for users who want to use Speechify Tom as the CAP alert TTS voice (this requires the full version), while the minimal version is for users who want a smaller footprint or have specific requirements (this version uses the Piper TTS engine instead).

**EAS Message Handling**: The core functionality of the project revolves around receiving EAS messages, which are typically broadcast over Icecast streams (which the user adds via config.json, the project supports "infinite sources", meaning there is no hard limit, only resource constraints). The codebase includes modules for parsing these messages and extracting relevant information. One core module is E2T-NG, which is responsible for converting EAS messages into a format that can be easily understood by humans. See https://github.com/wagwan-piffting-blud/E2T-NG for more details.

**Relaying Mechanisms**: After processing the EAS messages, the project can relay the information to various endpoints. The codebase includes support for Apprise, which allows for sending notifications to multiple platforms (like email, SMS, and messaging apps). Additionally, it supports Icecast for streaming audio alerts and MYOD for custom DASDEC-type implementations.

**Configuration**: The project uses a configuration file (config.json) to manage settings such as the list of Icecast sources, Apprise endpoints, and other parameters. Users can customize this file to suit their specific needs. The configuration file is crucial for the proper functioning of the listener, as it dictates how messages are received and where they are sent. The full configuration options, including examples, can be found at the GitHub wiki page at https://github.com/wagwan-piffting-blud/EAS_Listener/wiki/Configuration.

**How settings resolve**: every key is read by `Settings` in `src/config.rs`, which checks the environment first and config.json second, so a setting behaves the same wherever it is written. A blank environment variable counts as unset and cannot mask config.json. Docker flips that order: `docker_entrypoint.sh` exports config.json into the environment for its own startup logic, and sets `EAS_CONFIG_PRECEDENCE=file` so the listener reads config.json first and the environment second. With the old environment-first order that boot-time copy outranked the file forever, so an edit saved from the dashboard and reloaded changed nothing until the container restarted. A key only in `.env` still takes effect, because config.json is silent about it. Keys the entrypoint overrides on purpose -- a TTS engine the image lacks, a `LOCAL_DEEPLINK_HOST` given to the container -- go in `EAS_CONFIG_FORCED_KEYS`, and their environment value wins either way. Arrays arrive as real arrays from config.json and as JSON text from the environment, which is what the entrypoint's `@json` produces; booleans accept `true`/`yes`/`on`/`1` and their negatives from either source.

**Adding a configuration knob**: the `config_knobs!` table near the top of `src/config.rs` declares each one exactly once -- field, type, `Settings` accessor, config.json key, default -- and generates the struct field, the default and the code that applies it. A knob of that shape means adding one line there, plus its form field (below). Knobs needing more than "read the key, assign it" (paths anchored to the state directory, `MONITORING_BIND_ADDR`/`PORT`, `ENDEC_MODE` validation, `CAP_ENDPOINTS`) are declared in the `derived` block and handled by name in `apply_derived_knobs`. `Config::safe_internal_defaults` and `Config::from_config_json` both go through `Config::resolve`, so no key can be honoured by one and ignored by the other -- which is exactly the bug that made `ENDEC_MODE` in config.json do nothing outside Docker. `every_plain_knob_is_read_from_either_source` guards the table against regressing. Every knob also needs a `Field` in `src/config_schema.rs`, which is what the configuration form and first-run setup are built from: its group, label, help text, input kind and whether a reload applies it. Defaults there are read off `Config::defaults()` rather than restated. `the_schema_describes_exactly_the_keys_resolution_reads` fails when a key is read without a field or has a field without being read; it works by recording every key `Settings` is asked for while resolving, so the list of keys cannot fall behind the code.

**Testing configuration**: config tests never touch the process environment. `Settings::isolated` resolves against an environment map the test supplies, because the real environment is shared by every test running in parallel -- a test that sets a real config key races any other test that resolves config, in any module. The single test that exercises the real environment does it through a key no setting uses (`EAS_LISTENER_SETTINGS_SELF_TEST`).

**Logging and Monitoring**: The codebase includes logging functionality to track the processing of EAS messages and any errors that may occur. This is important for debugging and ensuring that the listener operates correctly. Users can configure the logging level in the configuration file.

**Web Server**: The dashboard is served by the Rust binary itself, from the axum server in `src/backend.rs`. There is no PHP, nginx or php-fpm any more: `web_server/` is plain static HTML, CSS and JavaScript, and everything dynamic is a JSON endpoint under `/api/`. The dashboard and the API share one port (`MONITORING_BIND_PORT`, 8080 by default) and one session. `src/web_assets.rs` is the only thing that serves a file: `build.rs` walks `web_server/` at compile time and writes a sorted `(path, content type, bytes)` table of `include_bytes!`, and `web_assets::read` prefers a copy on disk when `paths::web_root()` has an `index.html` (a checkout, the image, or `EAS_WEB_ROOT`) and uses the baked-in table otherwise. `ServeDir`/`ServeFile` are gone, so both sources go through the same path check -- `safe_relative_path` refuses `..`, absolute paths, backslashes and percent-encoding -- and the same `no-cache` headers. The gating is unchanged: only `login.html`, `login.js`, `style.css`, `favicon.ico` and `site.webmanifest` are reachable signed out; everything else is behind `page_auth` through the fallback. `build.rs` skips `web_config.json` and `image_info.json`, which are runtime artifacts and gitignored -- `web_config.json` carries the local configuration and must never end up in a published binary -- and a `const` assertion in `src/web_assets.rs` fails the build if the table comes out empty, which is what a Dockerfile that forgot to copy `web_server/` would produce. The builder stage copies it for that reason; the image still ships `/app/web_server`, so a container serves the files on disk and the built-in copy is the fallback.

Authentication is a session cookie set by `POST /api/login`, holding the same `base64(username:password)` token the API has always used. `request_is_authorized` in `src/backend.rs` accepts that token from an `Authorization: Bearer` header, the `eas_session` cookie, or an `auth` query parameter -- the cookie is what lets `<audio>` elements and the WebSocket authenticate, since neither can set a header. Pages are gated by a redirect to `/login.html`; the API returns 401.

**Paths and components**: `src/paths.rs` resolves everything relative to the application root -- `EAS_APP_ROOT` if set, otherwise the executable's own directory (or the crate root under `cargo run`). Nothing is hardcoded to `/app`. `src/components.rs` resolves the external binaries the listener shells out to (ffmpeg, ffprobe, icecast2, apprise, and the TTS engines) in the order: config.json key, then the install's `tools/` directory, then `PATH`. A missing required component stops startup with a message naming it; `GET /api/components` reports what was found.

**TTS engines are fetched, never vendored**: `spfy_synth`, `cep6` and `loqdave` each live in their own repository (Speechify, cep6-rs, ENDEC_Dave) and are pinned by release tag and SHA-256 in `tools/components.json`, like ffmpeg. The manifest is templated (schema 2): a GitHub-hosted component gives `github`, `release_tag` and a per-platform `asset`, the URL is implied, and `{tag}`/`{version}`/`{github}` are substituted in its strings -- by `RESOLVE_FILTER` in `fetch_components.sh` and `Resolve-Manifest` in `fetch_components.ps1`, which must stay in step. Pins are bumped only with `tools/update_components.py <component>` (digests from GitHub's release asset `digest`; `--check` verifies, `-n` diffs), which writes the file in its exact layout; it is a maintainer tool and not shipped in release archives. `.github/workflows/components.yml` runs it daily, one matrix leg and one `components/<name>` pull request per component (peter-evans/create-pull-request, which also deletes the branch once main already has the bump). Those PRs come from `GITHUB_TOKEN` and so trigger no other workflow, which is why each leg runs `fetch_components.sh` on the bump itself before opening one. Nothing about them is in git, in the image or in a release archive, so a takedown upstream is a failed download rather than a history rewrite or a pulled image. `fetch_components.sh` has two install types for them: `binary` (the release asset is the executable) and `archive` with an optional `data` list, which copies a directory out of the archive -- Speechify's Tom -- matched by the end of its path. `-d ROOT` installs binaries into `ROOT/tools` and data under `ROOT`; the Docker entrypoint uses it with the state volume for the engine `TTS_ENGINE` selects (Speechify when unset, in the full variant), prepends `ROOT/tools` to `PATH` so `engine_available` and `components.rs` find it, and exports `SPFY_VOICE_DIR` only if config.json did not set one. Each install writes `.<component>.sha256`; a manifest pinning a different digest replaces the install on the next run, and a missing stamp is trusted so pre-stamp installs are not re-downloaded. Inside the fetchers, never wrap a call in `set +e`/`set -e`: that re-enables errexit inside the caller's own `set +e`, and the next non-zero return ends the script -- use `|| return $?`. loqdave now carries Dave in the binary, and `--data` *replaces* that voice tree, so `run_tts_engine` passes it only when `LOQ6_DATA_DIR` is non-empty, which it is not by default. loqdave also reads its input as Latin-1 (`InputTextCoding=ansi`), so `to_latin1` writes that engine's file: Latin-1 as is, typographic quotes, dashes and ellipses as ASCII, anything else as a space.

**The alert stream serves itself**: `src/alert_stream.rs` replaced both `icecast.rs` and the bundled Icecast daemon. The pacing loop is unchanged (100 ms PCM chunks, comfort noise between alerts); ffmpeg now encodes to its stdout, `read_pages` cuts that into Ogg pages with `OggPageReader`, and `StreamHub::publish` broadcasts each one. The hub keeps the current stream's header pages -- from a BOS page through every page at granule 0 or -1 (a header split across pages) -- and `join` hands a new listener those plus a receiver under the same lock, so a listener joining while ffmpeg restarts neither misses the new headers nor gets them twice. The HTTP side is its own axum server on the dashboard's IP and `ICECAST_ALERT_PORT`, serving only `ICECAST_ALERT_MOUNT`; it rebinds when either changes on reload, so neither needs a restart. `ICECAST_ALERT_PORT` must differ from the dashboard's port. `ICECAST_ALERT_HOST`, `ICECAST_ALERT_SOURCE_USER`/`PASSWORD`, `ICECAST_PATH`, `START_ICECAST` and the entrypoint's Icecast launch are gone; an old config.json that still has them is simply ignored for those keys. **ffprobe is gone too**: its only use, `relay::probe_icecast_format`, listens to the destination mount for 64 KB and hands it to symphonia (`probe_stream_head`), with the bitrate from Icecast's `icy-br`/`ice-audio-info` headers; the fixtures it is tested on are excepted from `.gitignore`'s `*.mp3`/`*.ogg`. **Apprise is fetched as apprise-go** (Unraid's Go port, BSD-2-Clause): a single static `binary` component installed as `tools/apprise`. It takes the same argv as the Python Apprise, which is all `webhook.rs` relies on (`--title`, `--body`, `--input-format`, `--attach`, URLs, exit code). One behavioural difference: with `--input-format markdown` to a plain-text service it strips the markdown syntax, where Python Apprise passes it through. The Docker image fetches it at build time instead of installing Debian's `apprise`. **`apprise.yml` is edited from the dashboard and setup** (`src/notifications.rs`, `web_server/notifications.js`): `GET/PUT /api/notifications` read and rewrite it as `targets` (`notifications::Target` = url + `sources` + `events`, empty meaning all; `.bak` kept; the dashboard always writes the running config's `APPRISE_CONFIG_PATH`, setup the path in the config being saved; a PUT with the old `urls` array still works), `/api/notifications/services` is `apprise --schema` trimmed and cached per binary, and `POST /api/notifications/test` sends one URL a test (Discord natively, the rest through Apprise). The file is parsed with `serde_norway`: a YAML list of bare URLs or `{url, sources, events}` maps; anything that is not a YAML list falls back to the old one-URL-per-line reader. `render` writes JSON-quoted strings and arrays, which are valid YAML and spare quoting rules. **Routing**: `send_alert_webhook` keeps the targets whose `Target::accepts(Source, event_code)` is true; `Source::of_raw_header` reads the header's sender (`cap::cap_feed_of_raw_header`: `IPAWSCAP`/`IPAWSWEA`/`NAADSCAP`, anything else `offair`, including the test alert's `EASLSTNR`). Routes narrow after `FILTERS`, never widen. **Apprise is fetched on demand** via `notifications::ensure_apprise` (`components::ensure(&APPRISE)`): before `services()`, before a non-Discord test, in the background after a save containing a non-Discord URL, and before an alert's Apprise call. The page only asks for the service list on load when a non-Discord target exists, so a Discord-only install is not made to download it; a failed catalog load resets `catalogPromise` so the next attempt re-asks. `/api/setup/notifications*` mirror them behind the setup token. The builder picks the template with the most placeholders it can fill; values are `encodeURIComponent`-ed, which Apprise unquotes. apprise-go's `-d/--dry-run` still sends, so never use it as a validity check. `components::binary` resolves tools-dir-then-PATH before any config is loaded, so setup finds the bundled Apprise.

**Starting at boot**: `--install-service` means the same on every platform -- register to start automatically and start now -- through `src/service.rs` (Windows, `sc.exe`, needs the `service` feature), `src/systemd.rs` (Linux, any build) or `src/launchd.rs` (macOS, any build). On macOS root gets a LaunchDaemon (`/Library/LaunchDaemons`, `UserName` = the app root's owner) and anyone else a LaunchAgent (`~/Library/LaunchAgents`, `gui/<uid>` domain, starts at login, can show the menu bar icon); `render_plist` writes it for the actual install with Homebrew's folders on `PATH`, `KeepAlive.SuccessfulExit=false` and `launchd.log` beside config.json, and setup offers it as `automatic` (`launchd_daemon`/`launchd_agent`) since neither needs asking for rights. From SSH an agent still bootstraps if the owner is logged in at the desktop, otherwise it waits for the next login. `setup::desktop_session` (DISPLAY/WAYLAND_DISPLAY on Linux, `launchctl managername` == `Aqua` on macOS) decides both whether setup opens a browser and whether a `tray` build shows its icon or runs headless; the tray is created on `StartCause::Init` (macOS requires the loop to be running), menu clicks arrive through an `EventLoopProxy`, and the listener's task ending ends the tray with an error so a service manager sees the failure. `paths::is_root`/`user_name` use libc (unix only). **Components are fetched on demand** (`components::ensure`/`refetch`/`ensure_cepstral_voice`, all through `run_script` + `fetch_once`): a missing ffmpeg at startup, and the configured TTS engine plus its voice via `cap::ensure_tts_engine`, which runs in the background after startup and each reload (`prefetch_tts_engine`) and again before synthesis (both in `synthesize_tts_samples`, ahead of the voice checks, and in `run_tts_engine`). `fetch_once` runs the script in its own task (an alert's deadline cannot kill a download), serializes all fetches, and remembers a failure -- including "the script succeeded but installed nothing", i.e. no build for this platform -- for 10 minutes. A `Configured` path is never fetched over. On Windows the script runs under `powershell.exe` with `PSModulePath` removed (inherited from PowerShell 7 it breaks module autoload). `ComponentSpec.manifest` names the manifest entry; `resolve_in` also finds `tools/<manifest>/<binary>` for `"layout": "directory"` components (Piper). Manifest `files` are extra pinned downloads into the install root (Piper's model); a platform entry's own `files` are added to them (Speechify's bare Windows exe gets Tom from the repo's raw URLs at the release tag). Whether a download is unpacked follows the platform's `archive`, never the component's `install` type. Piper has no macOS pin (upstream's macOS archives are x86_64 and miss libespeak-ng); espeak-ng is `install: system`. `release.yml` also runs on pushes to main that touch `Cargo.lock`/`Cargo.toml`/itself (and by hand with an empty tag). On such a push `meta` reads `Cargo.toml`'s version: with no `v<version>` tag on the remote it is a release (`meta.outputs.release` true, jobs check out `meta.outputs.ref` = the pushed sha, and publish creates the tag there via `target_commitish`; a GITHUB_TOKEN-made tag starts no second run); with the tag already there nothing is signed or published. Runs on main are the only ones whose `rust-cache` saves (`save-if` main). That is deliberate: GitHub scopes caches to the ref, so a tag run can restore only its own tag's cache or main's, and before this every release compiled every crate from scratch. `release.yml`'s `macos` job builds both Apple targets on `macos-15`, joins them with `lipo`, and signs/notarizes only when `MACOS_CERTIFICATE_P12_BASE64` and `APPLE_API_KEY_P8_BASE64` are set (job-level `SIGNING` env): a throwaway keychain, `codesign --options runtime --timestamp`, a `.dmg` signed, notarized with `notarytool` (App Store Connect API key) and stapled; the tar.gz's binary is covered by the same notarization online. Unsigned, it still ships the tar.gz with a warning. Publish takes `dist/eas-listener-*` so a missing `.dmg` does not fail the release. The alert stream is Ogg Vorbis unless `ffmpeg -encoders` lacks libvorbis (Homebrew's ffmpeg), when it is Ogg Opus -- `alert_stream::stream_codec`, cached per ffmpeg path. The systemd unit is rendered by `render_unit` for the actual install (canonical exe, app root, `User=` the app root's owner unless root owns it) rather than shipped as a template, and `ExecStart` passes `--service`, which on Linux only marks the process as a service. Before writing the unit, `return_to_owner` gives root-created files inside the install back to that owner, without following symlinks: `config.json` written by a first-run setup answered as root would otherwise be read-only to the unit. **Instances** (`src/paths.rs`, `src/instances.rs`): `paths::install_root()` is what every instance shares (exe dir; crate root under cargo; `EAS_INSTALL_ROOT`; in the image `EAS_APP_ROOT`=/app) -- tools, voices and their scripts, `web_server/`, `image_info.json`. `paths::app_root()` is the instance's own directory -- config.json, apprise.yml, setup-token.txt, signal files, web_config.json, launchd.log/service-error.log, and the default `SHARED_STATE_DIR` (`<app root>/data`, service or not; the shared temp folder is gone). It is `EAS_APP_ROOT`/`--app-root` when set, the crate root for the default instance under cargo, else `paths::instances_dir()/<name>` (`%ProgramData%\eas-listener`; Linux `/var/lib/eas-listener` for root, `$XDG_DATA_HOME`/`~/.local/share` otherwise; macOS `/Library` or `~/Library/Application Support`). `main` parses `--instance`/`EAS_INSTANCE` (`paths::parse_instance_name`: `[A-Za-z0-9_-]`, lowercased, `default` = none) and `--app-root` before anything resolves a path, then `paths::prepare_instance` sets APP_ROOT: a default instance whose config.json is still beside the binary is migrated (`migrate_default_instance` copies config.json/apprise.yml/.bak files/the replacement dictionary, renames the originals `*.migrated`, moves `data/` or the old temp state dir into `<app root>/data` or pins `SHARED_STATE_DIR` to it when the rename fails) -- unless a default service is installed or this run is `--uninstall-service`, in which case the legacy folder stays in use. **Fetched assets are shared across instances and accounts**: `paths::shared_roots()` = install root, this account's `instances_dir()`, and root's system instances dir (readable by all). `paths::assets_root()` is the first of those whose `tools/` this process can write (else the app root) -- where fetches install (scripts take `-d`/`-InstallRoot`). `paths::tools_dirs()` searches all of them (`components::resolve_in`); `paths::find_shared` gives Tom's and Piper's default paths as the first existing copy, else under `assets_root`. Cepstral voices default to `paths::cep6_voice_dir()` (`assets_root/tts_voices/cep6`) outside the image (`config::cep6_voice_default`; in the image still `SHARED_STATE_DIR/tts_voices/cep6` on /data), and `cap::cepstral_voice_dir` also searches every shared root and the old `<state dir>/tts_voices/cep6`. The shell scripts run with `umask 022` (and `chmod -R a+rX` installed voices), and `paths::writable` widens a directory it made to 755, so a root/service fetch under umask 077 stays usable by other accounts; Windows relies on ProgramData's inherited Users read/execute ACL. Never add a world-writable shared dir: root-run listeners execute from these. Services are per instance: `service::service_name()` (`EASListener[-name]`, display "EAS Listener (name)"), `systemd::unit_name()` (`eas-listener[-name].service`), `launchd::label()` (`...eas-listener[.name]`); each passes `--service [--instance name] --app-root <dir>`. The default instance keeps the old names. `systemd::sudo_command` builds the sudo hint with `--app-root`, since root's instances live elsewhere. Setup's `choose_ports` (outside the image and unless the environment sets the port) moves off ports `instances::ports_taken_by_others` lists or that `instances::in_use` finds taken -- a bind is not enough on Windows, where Docker Desktop's and WSL's SO_REUSEADDR listeners let a second socket bind, so loopback connects count too -- and `schema_handler` offers the chosen dashboard and stream ports as defaults. `--list-instances` prints `instances::all()`. **`--uninstall`** (`src/uninstall.rs`) removes one instance: refuses in the image, asks for the instance name unless `--yes` (and refuses without a terminal), removes the service (Windows elevates through `service::uninstall_elevated`, the same `run_elevated` PowerShell hop install uses; Linux and a macOS LaunchDaemon bail with `systemd::sudo_command("--uninstall")` when not root), refuses while `instances::answers` finds its port taken, then deletes only `INSTANCE_FILES`, the state dir only with `--delete-data` (the alert archive is kept by default; `instances::all()` counts a folder as an instance only when it holds `config.json` or `setup-token.txt`, so a kept archive neither lists nor blocks `--with-program`), and -- when the folder is not the install root -- its own `tools/`/`tts_voices/`/`piper/` and the folder if now empty. `--with-program` (dashboard checkbox too), once `instances::all()` is empty, runs `remove_tools_and_program`: `remove_fetched` on every shared root, then `remove_program`, which deletes by name only the binary (when it sits in the install root) and `PROGRAM_FILES` + `SHIPPED`, then `rmdir`s their folders if empty -- never from a checkout (`Cargo.toml`). Unix unlinks directly; Windows cannot delete the running exe, so it schedules a `cmd /d /s /c "ping -n 4 ... & del ... & rmdir ..."` through `spawn_detached` (CREATE_NO_WINDOW, not DETACHED_PROCESS -- detached, cmd's ping opened a console window -- cwd the temp dir so it holds no folder being deleted, and every path with `/` turned into `\`, since cmd reads `/` as a switch even inside quotes). Never `remove_dir_all` on an `--app-root` or `SHARED_STATE_DIR`. `--uninstall --all` re-runs itself per instance (`--app-root <dir> [--instance name] --uninstall --yes [--delete-data]`, so each names its own service), then `remove_tools_and_program`; `remove_fetched` takes everything under `tools/` and `tts_voices/` except `SHIPPED`, plus `piper/` and `tts_voices/spfy/voices`. `prepare_instance` treats `--uninstall` like `--uninstall-service`: no migration on the way out. **From the dashboard**: `web_server/uninstall.js` (`window.UninstallPanel`, appended last in `config.js`, which keeps "Other keys" before it) reads `GET /api/uninstall` (`uninstall::plan`: folder, kept state dir, service, other instances, `allowed`/`reason`/`command`, `prompts` for a Windows UAC hop) and `POST /api/uninstall {confirm, delete_data, with_program}` runs `uninstall::start_from_dashboard`, which spawns `--app-root <dir> [--instance n] --uninstall --yes --wait [--delete-data] [--with-program] --log <temp>/eas-listener-uninstall-<name>.log` detached; the handler then `process::exit(0)`s after 1 s unless removing the service is what stops this process (`service_stops_it`). The helper's `--wait` gives the port 60 s to free. On Windows it is started through a hand-declared `CreateProcessW` with `bInheritHandles = FALSE` (`spawn_helper`) -- Rust's `Command` always inherits, and the helper then held the dead listener's listening socket and waited on its own port forever -- so it redirects its own output with `SetStdHandle` (`log_to`; `dup2` on Unix). On Unix the helper gets `process_group(0)` so launchd's bootout does not take it, and from a systemd unit it runs via `systemd-run --collect` since stopping the unit kills its whole cgroup (untested: no systemd in the test containers). The tray's **Uninstall…** opens `/config.html#cfg-group-uninstall`. `sync_web_runtime_config` writes `web_server/web_config.json` only when `web_root()` has an `index.html` (a checkout or the image), so a release never creates `web_server/` beside the binary. Release archives hold their files at the top level (`cd stage && tar -czf ../x.tar.gz *`, `Compress-Archive stage/*`); never `tar -C stage .`, whose `./` entry resets the permissions of the folder it is unpacked into. First-run setup asks via `autostart::availability`, served token-gated at `/api/setup/autostart`: `unavailable` inside this project's image (identified by `EAS_IMAGE_VARIANT`/`EAS_RESTART_AFTER_SETUP`, not `/.dockerenv` -- a container that boots systemd can take a unit), already a service, already installed, or no systemd; `automatic` when it can install (root on Linux; on Windows elevated, or not elevated but the page is on this machine, since `is_local_peer` decides who could answer the UAC prompt); otherwise `manual` with the command. The page requires an answer when it offers the choice. `PUT /api/setup/config?service=install` installs after config.json is saved and re-checks availability server-side; on success `setup::run` returns `Handover::Service` and `run_listener` exits 0 so the service takes the port (`bind_with_retry` covers the gap); on failure this process starts the listener as usual and the page shows why. The Windows elevation runs this exe's own `--install-service` through PowerShell `Start-Process -Verb RunAs`, with paths passed in the environment so nothing in them is parsed as PowerShell.

**Docker healthcheck**: the `HEALTHCHECK` process gets the image's `ENV` but not what the entrypoint exports from config.json, so it cannot know `MONITORING_BIND_PORT` -- the old `curl localhost:${MONITORING_BIND_PORT}` probed an empty port and every container reported unhealthy. Instead `backend::bind_with_retry`, which both the listener and first-run setup bind through, writes the address it actually bound to the file named by `EAS_HEALTH_ADDR_FILE` (`/tmp/eas_listener.addr` in the image; unset elsewhere, so nothing is written), using loopback when bound to every interface (`health_address`). The entrypoint deletes the file on start because `/tmp` survives `docker restart`. The start period is 120 s because a first boot downloads the TTS engine before binding.

**Standalone builds**: the binary is a complete install on its own -- the dashboard is compiled into it -- and writes `config.json` beside itself on first run. Two optional features, both off by default so container builds are unaffected: `tray` adds a desktop system-tray icon (`src/tray.rs`), and `service` adds Windows service registration (`src/service.rs`, `--install-service` / `--uninstall-service` / `--service-status`). The service host answers the Service Control Manager handshake via the `windows-service` crate; `--service` is what the SCM invokes and is not useful from a terminal.

**Reload and test alerts** are in-process channels. `POST /api/reload` and `POST /api/test-alert` hand a request to the task that services it over a depth-1 `mpsc`, so a second request while one is pending coalesces. The legacy `reload_signal` and `test_alert_signal` files still work: `run_signal_file_watcher` in `src/main.rs` polls for them once a second and feeds the *same* channels, so there is still exactly one reload path and one test-alert path. Both files now resolve through `paths::reload_signal()` / `paths::test_alert_signal()` rather than being pinned to `/app`. `take_signal_file` consumes a signal by deleting it, which is what makes the next `touch` a fresh request.

**CAP recording framing**: `recording_framing` in `src/cap.rs` decides once per alert, in `process_cap_alert`, between `RecordingFraming::Same` (header, attention tone, message, NNNN) and `RecordingFraming::AlertReady` (the Alert Ready attention signal once, a second of silence, the message, nothing after). `AlertReady` needs both `CAPCP_USE_ALERT_READY_TONE` and a NAAD source, as judged by `cap_header_source_marker` -- which covers live `naad://` documents and ones recovered from the `capcp*.naad-adna.pelmorex.com` archive alike. The same decision keeps the SAME header out of webhooks: `send_alert_webhook` takes the header to publish as an `Option`, and every body renders its "EAS Protocol Data" section only when given one. The raw header is never removed internally -- it is the alert's identity in active state, the database and recording metadata. The tone is `include/pelmorex.wav`, compiled in with `include_bytes!` so neither a standalone binary nor the image needs `include/` at runtime. Both framings build on `concat_recording`, which owns the ffmpeg invocation and storage-saver handling. A CAP recording's filename ends in the feed it came from -- `IPAWSCAP`, `IPAWSWEA` or `NAADSCAP` -- taken from `cap_header_source_marker(&alert.source_url)`, the same call that picks the header's sender ID, so the two cannot disagree. (It used to be re-derived from the header by a check that only knew WEA, which labelled every CAP-CP recording `IPAWSCAP`.) `RecordingFraming::Bare` is the third outcome and outranks the other two: `EMIT_HEADER_TONES` set to `false` frames nothing, so the recording is the message audio concatenated on its own -- still through `concat_recording`, so its name and format are unchanged -- and, like `AlertReady`, it publishes no header. `Config::header_audio_override` is the one place `CUSTOM_HEADER_AUDIO` is resolved: it returns the path only when the tones are on and the file is still readable. `Config::capcp_header_audio_override` is its CAP-CP counterpart (`CAPCP_CUSTOM_HEADER_AUDIO`, falling back to the shared key only when empty), and `cap::header_audio_for` picks between them by source marker (NAAD or not); both builders swap the result in for their opening segments (the SAME header plus attention tone, or `pelmorex.wav`), leaving the closing NNNN alone. `src/recording.rs` reads the same two knobs for off-air recordings, where the custom file is decoded through `decode_audio_file_to_i16`; it keeps generating the NNNN burst even when it will not write one, because `detect_trailing_nnnn_start` sizes its search from it to trim the station's own NNNN out of the captured tail.

**NOAA Weather Radio streams**: `Config::stream_is_nwr` is the only thing that decides whether the 1050 Hz tone is listened for, and `process_stream` in `src/audio.rs` asks it per chunk -- a stream worker survives a reload, so reading it once per connection would pin the answer until the stream dropped. Unmarked, the chunk never reaches `NwrToneDetector::process` and `ToneSustain` is held reset, so nothing accumulates while a stream is off the list. The backing knob is `ICECAST_STREAM_NWR`, a list of stream URLs (matched against the same URL that is the stream's label everywhere else), declared as `Option<HashSet<String>>`: `None` is the key being absent, which watches every stream, because that is what installs predating the key do and silently losing NWR recordings on upgrade is worse than a broad default. An empty list is a real decision and watches none. The schema's default for it is `Value::Null` rather than `[]` for the same reason -- the form's "same as the default, so do not write it" rule would otherwise collapse an explicit empty list back into an absent key. The stream list in `web_server/config-form.js` renders the tick per row (`Kind::StreamList` carries `nwr_key` beside `nicknames_key`), starts every row ticked while the key is absent so the form shows what is actually happening, and only writes the key once a row is cleared. SAME decoding is not gated by any of this: every stream goes through `same_receiver` whatever its mark.

**TTS replacements**: `TtsReplacements` in `src/cap.rs` is the only place `cap_tts_replacement_config.json` is applied, once, in `synthesize_cap_tts_audio`, to the opening sentence, the description and the instructions alike. It compiles every key into one alternation -- longest first, whole-token (`replacement_key_pattern` adds `\b` on word-character edges), smartcase (an all-lowercase key matches any case) -- and replaces in a single pass, so no output is re-matched and the file's order is irrelevant. `apply_to_prose` skips URL and hashtag spans using the same `url_regex`/`hashtag_regex` that `normalize_text_for_speech` uses, and runs before it, so the dictionary never sees Speechify's spell-mode control codes. `sanitize_cap_description` used to apply the dictionary as well, at parse time, case-insensitively and in `HashMap` order; that pass is gone. There is one engine-neutral dictionary (`cap_tts_replacement_config.example.json`), not one per engine, and it is compiled in and applied by default (`TTS_BUILTIN_REPLACEMENTS`), with the user's own file laid over it; the Dockerfile's builder stage copies it for that reason.

**CAP-CP streams and recovery**: each NAAD stream's reader only reads. A live document is marked handled by its identifier (`naad:<identifier>`, so the second stream's copy stops there) and processed on a detached task, so narration or a relay never holds up the next document; a reload cannot cut it off halfway either. Heartbeats go to one recovery worker over a small queue, which fetches the alerts they list that were never seen, asking both archive hosts at once and taking the first answer. It used to do this inline on the reader, one host after the other with a 10 s timeout each, so with one stream down the surviving one sat unread for tens of seconds per heartbeat. What was handled -- identifiers for 30 days, dedupe keys until the alert expires -- is kept in the `cap_seen` table rather than only in memory. The readers and the worker belong to a `JoinSet` owned by the processor task, so the abort a reload sends it takes them along; before, they were detached and each reload left the old readers running beside the new ones.

**SAGE HelloTTS**: `src/hellotts.rs` reproduces the Rev96 SAGE 3644 `loq/HelloTTS` rewrite, routine by routine from its disassembly, and `synthesize_cap_tts_audio` applies it to the opening sentence when the engine is Loquendo and `ENDEC_MODE` is SAGE. Only text it recognises changes: a SAME sentence starting with one of its five preambles and carrying "beginning at", "and ending at" and "(", or CAP text marked "(fromcap)". The call sign in parentheses after the end time is cut, which is why a real SAGE never reads it. `TTS_READ_CALLSIGN` (off by default) does the same for every mode and engine, through `strip_sender_clause`. E2T's SAGE mode uses the Rev96 preambles for PEP ("The United States Government") and EAN ("The Emergency Action Notification Network"), so every originator's sentence is one HelloTTS recognises. `build_eas_text` takes the ENDEC mode from the config it is handed, not `Config::get()`, which is loaded once and ignored reloads.

**Telling CAP alerts apart**: `cap::is_cap_raw_header` is the one Rust classifier for "did this alert come from a CAP feed". It matches the header's sender ID exactly against the three markers -- `IPAWSCAP`, `IPAWSWEA`, `NAADSCAP` -- which live beside it in `src/cap.rs`. The CAP status count and the "skip an off-air alert that duplicates an active CAP one" check both use it; each used to test for `"IPAWS"`, which silently left CAP-CP out. A CAP feed is not registered as a monitored audio stream (`process_cap_alert` passes no source to `broadcast_alerts`), so nothing has to filter CAP endpoints back out of the stream list by URL. The CAP status payload describes both feeds: `enabled` is either one, with `ipaws_enabled`/`capcp_enabled` and each feed's endpoints alongside, and the dashboard shows poll statistics only when IPAWS is on.

**Test alert narration**: `run_test_alert_handler` injects the synthetic RWT, then runs the configured engine over a generic script via `cap::synthesize_test_alert_narration` -- the same `synthesize_tts_samples` path CAP alerts take, under the same `cap_tts_synth_lock` -- and feeds the result into the empty body of the test alert's own recording through its `audio_tx`, converted by `recording::pcm_for_recording`. The recorder finalises only once every sender is dropped, so the handler's clone must be gone before it sends the NNNN; `narration_reaches_the_recording_and_releases_it` guards that. The handler takes reloads from its own `reload_rx`, so a changed `TTS_ENGINE` is used by the next test without a restart, and it waits for the recording to exist before sending NNNN rather than sleeping a fixed time. Test alerts (`stream_id == TEST_ALERT_STREAM_ID`) bypass the alert manager's duplicate check in both directions: their header is only unique to the minute, and a cached one could otherwise suppress a real national RWT sent in the same minute. `synthesize_tts_samples` also now fails fast, before halve-and-retry, on an unresolvable Speechify/Cepstral voice or an engine binary that cannot be started (`tts_engine_could_not_start`) -- retrying with less text cannot fix either.

**Editing configuration**: `GET /api/config` returns config.json verbatim and `PUT /api/config` replaces it. The candidate is validated by `backend::check_candidate`, which loads it through `Config::from_config_json` on a temporary file, so the editor's rules can never drift from the rules startup applies, and which also refuses credentials the dashboard would lock everyone out with. The live file is untouched until the candidate is known good, and the outgoing version is copied to `config.json.bak`. `?dry_run=true` validates without writing. `write_atomic` falls back to rewriting the file in place when `rename` fails, because Docker bind-mounts config.json as a single file and `rename` over a mount point is `EBUSY`. `config.html` renders the file as a form from `GET /api/config/schema` (`web_server/config-form.js`, shared with setup): an input writes its key, "Use default" deletes it, and keys the schema does not know are carried through untouched. The backend keeps its `Config` behind a lock updated from the reload broadcast, so changed dashboard credentials apply on reload; a reload whose credentials nobody could sign in with keeps the running ones.

**Where config.json is**: `paths::config_json()` is `<app root>/config.json`, unless that is a directory -- what Docker mounts when the host file did not exist before the first `up` -- in which case it is `config.json/config.json` inside it. That reaches the host through the same mount, so nobody has to fix the mount first. Everything reads the path through `paths::config_json()`, and the entrypoint resolves it the same way.

**No fallback to defaults**: `load_config` in `src/main.rs` has no fallback. A config.json that is present but does not load -- invalid JSON, or a value `Config::resolve` rejects -- stops startup with the reason, and a reload of one is refused while the running configuration stays in effect. The Windows service host turns a startup failure into a stopped service with a service-specific exit code and writes the reason to `service-error.log`, since it has no console. `Config::safe_internal_defaults` is still what first-run setup binds with, and what tests start from.

**First-run setup**: when config.json is missing, empty, `{}` or holds only `_comment` keys, `run_listener` runs `setup::run` instead of the listener: a small server on the configured bind address serving `setup.html` and nothing else, so no default stream is monitored and no default is written. An invalid config.json is not a first run -- it is someone's configuration with a typo, and it is refused as above. The setup page is opened in the default browser through the `open` crate on Windows, and on Linux only when `DISPLAY` or `WAYLAND_DISPLAY` is set, because without one xdg-open falls back to a text browser in whatever terminal started the listener. The Windows service never opens one; `--no-browser` and `EAS_NO_BROWSER=1` turn it off anywhere. Every setup API call needs the token printed to the console and written to `setup-token.txt` in the app root, since whoever reaches the port first could otherwise claim the install. Saving goes through the same `check_candidate`/`write_config` as the editor, writes only the keys the user filled in, and shuts the setup server down; the listener then starts in the same process. Under Docker the entrypoint sets `EAS_RESTART_AFTER_SETUP`, and the listener exits with 75 instead, so the entrypoint runs again and applies what only it applies (TTS engine resolution, starting Icecast). Both servers answer `/api/setup/status`, with `phase` telling the setup page which one it is talking to during the handover.

**Semantic Versioning**: The project loosely follows semantic versioning principles, with version numbers indicating the level of changes made. Patch versions are for bug fixes and minor improvements to the dashboard (`web_server/`), minor versions are for new features or bug fixes to the listener itself (`src/`), and major versions are mostly unused (per Rust ecosystem tradition).

**Releases**: When preparing a new release, run the following commands, in order, to ensure that the release is properly prepared for me to commit and push to GitHub (I handle all final commits). These commands will format the code, check for errors, run tests, and build the release version of the project:

```bash
cargo fmt
cargo check
cargo test
cargo build --release
```

The `tray` feature is not covered by a bare `cargo check`, so verify it separately when touching
`src/main.rs` or `src/tray.rs`:

```bash
cargo check --features tray
```

The dashboard has a browser-level smoke test that exercises login, the WebSocket, the archive page
and logout against a running instance. It is worth running after any change to `web_server/` or to
the routing in `src/backend.rs`. `tests/browser/setup.js` does the same for first-run setup, against
an instance started with no config.json.

If **ANY** cargo warnings or errors appear, the release should not be made until they are resolved. This project operates under a zero warnings policy, and any warnings or errors must be addressed before a release can be made. Note that releases are automatically built and pushed to GitHub Container Registry (GHCR) for Docker users, and the release process is automated to ensure that the latest version is always available for users.

Pushing a version bump in `Cargo.toml` to main (or a `v*` tag) also runs `.github/workflows/release.yml`, which builds standalone binaries for Linux x86_64, Linux aarch64 and Windows x86_64 (the Windows one with `tray,service`), starts each one with `--help`, packs the binary with the README, changelog, licence, examples and the `tools/` fetch scripts -- no `web_server/`, since the dashboard is in the binary -- and publishes them with a `SHA256SUMS` file. The release notes are the `## v<version>` section of `CHANGES.md`, which the workflow reads and never writes; without one it falls back to GitHub's generated notes. `workflow_dispatch` takes an existing tag and defaults to a draft. The Linux legs build on Ubuntu 22.04 on purpose: its glibc 2.35 is older than Debian 12's, so the binaries run there too, which binaries built on 24.04 would not.
